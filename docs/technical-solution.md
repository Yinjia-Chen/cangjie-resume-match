# 技术方案：基于仓颉语言的招聘简历筛选与智能匹配系统

## 1. 项目定位与范围

简历筛选是 HR 领域的高价值 AI 应用场景。本项目利用仓颉实现智能化简历分析、岗位匹配及面试辅助，输出可追溯的推荐结果并与人工筛选对比。

首选仓库名：`cangjie-resume-match`。
备选：`cangjie-cv-match`、`cangjie-resume-fit`。

设计原则：简单就是力量。采用仓颉主程序、一个文档解析工具、两个 Agent 和一个大模型 API；五个模块在同一仓颉项目内组织，两个 Agent 按固定流程调用。分阶段实现；当前已完成解析骨架、岗位模型和确定性评分，语义模型尚未接入。

## 2. 总体架构与任务对应

| 模块 | 职责与输出 | 对应任务 |
| --- | --- | --- |
| 简历解析与抽取 | PDF、Word、图片文本提取；抽取技能、工作经历、项目、学历及行为事例，保留原文证据 | ①多格式解析和信息抽取 |
| 岗位需求建模 | 岗位描述转为技能、经验、学历、软素质四维要求，支持 HR 修正必需条件和权重 | ②岗位知识表示 |
| 匹配与推荐 Agent | 逐项寻找证据，形成维度评分输入，计算总分、排序，生成优势、差距和待核实项 | ③智能匹配评分、④排序与推荐理由 |
| 面试问题 Agent | 根据岗位重点、简历项目及匹配差距，生成个性化问题、追问和考察要点 | ⑤面试问题生成 |
| 结果展示与评估 | 上传、岗位录入、候选人列表与详情；人工标注录入和评估报告 | ⑥与人工筛选对比及操作入口 |

采用单体应用，不引入向量数据库、消息队列或模型训练。文档解析作为本地外部工具复用，不单独建设业务服务。

## 3. 数据流与知识表示

1. 简历文件 → 文本及来源位置 → 简历结构化数据。
2. 岗位描述 → 四维岗位要求 → HR 确认。
3. 结构化简历 + 岗位要求 → 匹配 Agent → 仓颉计算分数与排序 → 推荐结果。
4. 按候选人需要调用面试问题 Agent。
5. 人工筛选结果与系统输出一起进入评估模块。

知识表示使用仓颉结构体 + JSON，无需知识图谱。

| 对象 | 最小必要字段 |
| --- | --- |
| 简历 | 技能、经历起止时间、项目职责及成果、学历、软素质行为证据 |
| 岗位要求 | 要求项、所属维度、目标水平、是否必需、权重 |
| 匹配结果 | 要求项、满足程度、原文证据、维度分、总分、缺口、待核实项 |

技能同义词用小型映射表统一，如 JS → JavaScript；相关工作年限按不重叠时间区间计算。缺失信息标为“未知”。软素质只依据简历行为事例初步判断，留待面试核实。证据保留原文片段及可获得的页码或段落位置。

## 4. 关键技术选型

| 技术 | 选择理由与边界 |
| --- | --- |
| 仓颉结构体 + 普通接口 + JSON | SDK 1.0.0、stdx 1.0.0.1；确定性评分由仓颉完成，语义判断预留接口；不使用 Magic DSL 或宏动态库 |
| Docling 本地解析工具 | 统一处理 PDF、DOCX、图片及 OCR；仓颉调用命令行读取 JSON；旧版 .doc 先转 .docx，转换工具在实施阶段确认 |
| 一个支持中文及结构化输出的大模型 API | 复用同一模型完成抽取、语义匹配、理由和问题生成；仓颉校验返回字段、数值及证据引用 |
| 本地文件 + JSON | 支撑毕业设计规模，保存原文、结构化结果、配置和评估记录，便于复现实验 |

仓颉负责格式分流、工具调用、信息抽取编排、结果校验及业务逻辑；底层文档解码和 OCR 并非仓颉原生实现，论文中应明确这一边界。

简历只解析和抽取一次，岗位修改后复用简历数据，面试题按需生成。低质量 OCR、解析失败或字段校验失败应显式标记为待处理，不生成看似成功的结果。

技术依据：

- [本地验证报告](local-validation.md)与[第二步实现说明](matching-implementation.md)：保留 SDK/stdx，放弃 Magic DSL。
- [Docling 支持格式](https://docling-project.github.io/docling/usage/supported_formats/)：PDF、DOCX、图片等文档输入。

Docling 本地解析已验证；语义模型 API 与面试接口尚未接入。

## 5. 匹配评分与候选人推荐

初始权重建议：技能 40%、经验 35%、学历 15%、软素质 10%。HR 可按岗位调整，并在评估前固定。

| 维度 | 判断依据 |
| --- | --- |
| 技能 | 必需技能覆盖程度、项目实际使用证据 |
| 经验 | 相关年限、职责相似度、项目复杂度和成果 |
| 学历 | 岗位明确提出的学历、专业要求 |
| 软素质 | 协作、沟通、问题解决的行为事例，作为低权重辅助信号 |

Agent 按固定评分量表返回逐项满足程度及证据，仓颉进行维度汇总与加权计算。维度分统一到 0～100，总分为各维度分数乘权重之和。具体满足程度映射及维度内权重在开发集确定，测试前冻结。

未知项不计作已满足，同时展示证据覆盖率（有可核实证据的要求项数 / 总要求项数），避免将“没有写”解释为“没有能力”。

必需条件独立标记“满足／不满足／待核实”。默认先展示满足组并按总分排序，待核实组交由 HR 复核；不满足组保留明确原因。推荐理由引用原文证据，同时说明优势与缺口。姓名、性别、年龄等非岗位能力信息不参与评分，最终筛选由 HR 决定。

匹配 Agent 输入：结构化简历、已确认岗位要求、固定量表。
输出：逐项满足程度、证据引用、维度评价、优势、缺口和待核实项。总分及最终排序由仓颉计算，推荐理由与计算结果保持一致。

## 6. 面试问题 Agent

输入：结构化简历、岗位要求、匹配结果及证据。

每位候选人生成约 5 道题，覆盖项目核实、核心技能、能力缺口和行为事例。每题包含问题、对应证据或缺口、考察要点及建议追问。题目应针对候选人经历，不把未证实的模型推测当作事实。

## 7. 准确率评估

### 数据与流程

建议准备 5 个岗位、约 200 份脱敏简历，形成约 300 个简历—岗位配对；包含匹配、不匹配及边界样本，并覆盖 PDF、Word 和图片。

1. 两名具备招聘或岗位知识的标注者独立盲评，标注“是否推荐面试”及 0～3 级相关性；分歧通过讨论或第三人裁决形成参考答案。
2. 按候选人划分开发集与测试集，避免同一简历跨集合泄漏；只在开发集调整提示词、权重及推荐阈值。
3. 固定模型、提示词、权重和阈值，在测试集运行本系统及“关键词覆盖 + 固定规则”基线。
4. 对比人工参考答案、规则基线和本系统；按岗位、文件格式分别报告，分析 OCR、抽取及匹配错误。

### 指标

| 指标 | 目的 |
| --- | --- |
| Accuracy、Precision、Recall、F1 | 衡量是否推荐面试；重点报告 F1 与 Recall，避免类别不均衡掩盖漏筛 |
| NDCG@10 | 以人工 0～3 级相关性评价排序质量 |
| 关键字段抽取 F1 | 以人工字段标注评价技能、学历、经历抽取，定位上游错误 |
| Cohen’s κ | 基于裁决前双人标注，评价人工标准的一致性 |
| 理由与面试题人工评分 | 评价证据真实性、岗位相关性和问题可用性 |
| 单份耗时、API 成本 | 评价实际筛选效率 |

所有指标作为实验结果报告，不预先宣称准确率。测试集不参与调参。推荐判断需明确使用总分阈值及必需条件处理规则；待核实样本单独统计，并报告覆盖率，避免通过排除困难样本虚增指标。

## 8. 阶段交付与实施边界

当前交付解析骨架、岗位 JSON/结构体、冻结评估配置、确定性评分排序、证据引用和语义判断接口；面试仅保留接口。

尚未接入语义模型、面试生成、UI、数据采集或准确率实验；模型不可用时保持未知、待核实，不生成虚构结论。
